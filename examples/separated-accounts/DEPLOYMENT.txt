Separated-account deployment (Linux/OpenSSH)
===========================================
The production boundary is operator-managed OS accounts plus the remote identity,
not a container sandbox supplied by estus. The acceptance container is disposable
test infrastructure only. MCP request policy does not restrict arbitrary execution
under the SAME identity as the service. Trusted controller scripts and Ansible
code run with service credentials: review them as service-account code. Projection,
no_log and cleanup do not sandbox that code.

Provision distinct unprivileged estus-client, estus-service and estus-target
accounts (target may be on another machine). Never grant estus-client sudo/su,
container-runtime access, service groups, ptrace rights or another path to service
execution. Do not share the service's UID with the MCP caller. Keep the service
login shell /bin/sh: ForceCommand runs via the login shell -c, not nologin. Disable
all other authentication/ingress for that service identity. Neither client nor
service may modify the root-owned sshd configuration, wrapper, estus executable,
server config, outbound config or ingress authorized keys.

Install the actual Linux estus package/closure at /opt/estus (a root-owned symlink
to an immutable Nix package works). Install estus-ingress and estus-record-identity
root:root 0755 in /usr/local/libexec; the latter belongs on the target machine.
Create /etc/estus root:estus-service 0750; install server.toml and
outbound_ssh_config root:estus-service 0640 there. Set the outbound HostName/Port
to the actual target. Keep /var/lib/estus-service and /run/estus-service owned
estus-service:estus-service 0700; persist the former and recreate the latter at
boot before accepting sessions (e.g. a tmpfiles.d entry:
    d /run/estus-service 0700 estus-service estus-service -
). The service's passwd HOME should be /var/lib/estus-service. No other user may
traverse these directories. Estus additionally creates owned mode-0700 /tmp/sm-*
directories for native SSH control sockets (it deliberately ignores TMPDIR for
those paths); the client must not gain traversal or socket access there either.

Generate an outbound ed25519 key AS estus-service; keep outbound_key mode 0600
in its private home. Install only its public key in the target account's
root-managed authorized keys. Pin the target host key in the service's known_hosts
from an authenticated operator source, not blind ssh-keyscan. Create the target's
/home/estus-target mode 0700 owned by estus-target for identity-evidence.

Generate a DIFFERENT ingress key AS estus-client, mode 0600, in its private home.
In /etc/estus/ingress_authorized_keys (root:root 0644) install exactly:
    restrict ssh-ed25519 <client-ingress-public-key> <optional-comment>
This public key logs in as estus-service, but only through forced MCP. It must NOT
appear in the target's authorized keys. Never distribute the outbound key to the
client. For multiple clients, use separately revocable ingress keys.

Use a dedicated sshd configuration with no global AcceptEnv directives, public-key
only authentication, pinned server host keys and the supplied sshd_config Match
block. Do not merge broad environment acceptance from another sshd; environment
can affect the login shell before the wrapper clears it. Check sshd -t before
starting/reloading. ForceCommand alone DOES NOT disable forwarding: retain both
DisableForwarding and restrict, plus no PTY/user rc/environment/tunnel. Restrict
network exposure to intended callers. Do not interpret SSH_ORIGINAL_COMMAND.

An MCP stdio client uses:
    ssh -T -i /private/client/ingress_key -o IdentitiesOnly=yes \
      -o IdentityAgent=none -o StrictHostKeyChecking=yes \
      -o UserKnownHostsFile=/private/client/pinned_ingress_hosts \
      estus-service@service-host
Initialize MCP and call record_identity with {"host":"target"}. No command,
program, argv, authority or SSH alias is client-selectable. The reviewed fixed
operation records target UID; generic ssh_exec/ssh_run/ssh_sudo are not exposed.
The outbound identity still has OS rights on the target, so enforce any narrower
remote-account policy there independently.

References (OpenSSH current manuals):
https://man.openbsd.org/sshd_config#ForceCommand
https://man.openbsd.org/sshd_config#DisableForwarding
https://man.openbsd.org/sshd#restrict

Disposable acceptance (never a production isolation claim):
Build .#packages.aarch64-linux.deployment-fixture-image (or x86_64-linux), yielding
image.tar.gz, image-ref and image-id. From nix develop, set ESTUS_TEST_FIXTURE to
that directory and DOCKER_HOST to the explicit owned Docker Unix socket. Run:
    cargo test --test deployment_boundary -- --ignored --nocapture
No host sudo is needed. Only disposable-container root performs setup/observation;
client probes and actual SSH MCP transport execute as UID 1200, the real Linux
estus server as UID 1201, and fixed remote work as UID 1202. The test's existing
fixture owner verifies the immutable image and removes both owned containers,
including processes, private credentials, temporary results and control sockets.
The deployment fixture omits OpenSSH's pre-authentication syscall sandbox because
guest seccomp cannot execute under cross-CPU Docker emulation and this kernel
rejects the portable rlimit fallback. Privilege separation, real UID drops and
every authorization assertion remain enabled. This does not alter the production
example's OpenSSH hardening and does not qualify SSH or container sandboxing.
